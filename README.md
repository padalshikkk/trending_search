Сервис агрегирует поисковые запросы из Apache Kafka, вычисляет топ‑N самых частых фраз за последние 5 минут и отдаёт их через HTTP API. Реализована защита от накруток, динамический стоп‑лист и кеширование для high‑load.

1\. Инструкция по локальному запуску и примеры запросов

Требования:

\- Docker Desktop (версия 29+)

\- Git Bash (или любой терминал)

Запуск:

Склонируйте репозиторий (или создайте файлы вручную)

git clone https://github.com/padalshikkk/trending\_search.git

cd trending-search

Запустите все сервисы:

docker compose up --build

После запуска сервис будет доступен на http://localhost:8080.

Примеры запросов к API:

\- Получить топ‑5 запросов

curl "http://localhost:8080/top?limit=5"

\- Управление стоп‑листом (скрытие нежелательных слов):

Добавить слово:

curl -X POST http://localhost:8080/stoplist -H "Content-Type: application/json" -d {"word":"iphone"}

Удалить слово:

curl -X DELETE "http://localhost:8080/stoplist?word=iphone"

Посмотреть все стоп‑слова:

curl http://localhost:8080/stoplist

\- Метрики Prometheus

curl http://localhost:8080/metrics

\- Отправка тестовых сообщений в Kafka (симуляция поисковых событий)

docker exec -it trending-search-kafka-1 kafka-console-producer --topic search-events --bootstrap-server localhost:9092

В интерактивном режиме вводите JSON‑строки:

json

{"term":"iphone","user\_id":"user1"}

{"term":"iphone","user\_id":"user2"}

2\. Контракт данных (формат сообщения в Kafka)

\- Пример payload’а

{

&#x20; "term": "iphone 15 pro max",

&#x20; "user\_id": "user\_12345"

}

Обоснование выбранных полей:

\- term (строка, обязательное) - поисковый запрос. Именно его частоту мы считаем для формирования топа.

\- user\_id (строка, обязательное) - идентификатор пользователя. Необходим для защиты от накруток: один пользователь не может бесконечно повторять один и тот же запрос. Лимит - 20 раз в минуту на пару (user\_id, term). Если бы мы не передавали user\_id, то не смогли бы отличить реальную популярность от действий парсера/конкурента.

Поле timestamp не передаётся, так как сервис использует собственное системное время для разбивки на окна. Это гарантирует единообразие и исключает зависимость от времени на стороне отправителя.

3\. Обоснование архитектуры и структур данных

Хранение топа - скользящее окно (in‑memory)

Структура: Кольцевой буфер из N бакетов (каждый бакет - map\[term]count).

Параметры по умолчанию: 5 бакетов по 1 минуте → окно 5 минут.

Почему именно так?

\- Производительность записи: O(1) - просто инкремент счётчика в текущем бакете.

\- Минимальные аллокации: бакеты переиспользуются, старые очищаются при вращении.

\- Точность: агрегация с точностью до 1 минуты достаточна для виджета «сейчас ищут» - пользователь не заметит погрешность.

\- Отсутствие внешних БД: данные живут только в памяти, при перезапуске статистика сбрасывается - это допустимо, так как виджет показывает актуальный «моментальный» тренд, а не историю.

Управление стоп‑листом:

Структура: sync.RWMutex + map\[string]struct{} (множество).

Почему?

\- Потокобезопасность при одновременных чтениях (в каждом запросе /top) и редких записях (добавление/удаление через API).

\- Поиск вхождения O(1), минимальное потребление памяти.

\- Динамическое изменение без перезапуска сервиса - соответствует требованию «на лету».

Кеш топа

Структура: struct { result \[]string; updatedAt time.Time } с sync.RWMutex.

\- Запросов на чтение (/top) в 10-50 раз больше, чем входящих поисковых событий.

\- Пересчёт топа на каждый запрос требовал бы O(U log U) (где U - уникальные термы) и блокировок. Кеш снижает нагрузку: топ вычисляется раз в TOP\_CACHE\_TTL секунд (по умолчанию 2). Остальные запросы получают закешированный ответ.

&#x20;4. Trade‑offs и бизнес‑логика: компромиссы ради производительности

&#x20;Выявленные проблемы в продуктовой постановке и их решения:

1 проблема:

Накрутки со стороны парсеров/конкурентов (аномальные всплески одного запроса)

Решение:

Rate limiter на пару (user\_id, term). Если один пользователь отправляет >20 одинаковых запросов в минуту - остальные игнорируются. Таким образом, даже тысяча запросов от одного пользователя не повлияет на топ.

2 проблема:

Требование максимально быстрой отдачи топа

Решение:

Кеширование ответа на 2 секунды + использование in memory структур. Среднее время ответа /top < 3 мс при 1000 RPS.

3 проблема:

Неточность в задании про «последние 5 минут» - не указано, нужна ли идеальная точность или допустима агрегация по минутам

Решение:

Выбрана агрегация с минутными бакетами. Компромисс: точность до минуты против сложности реализации точного sliding window с событийным удалением. Для виджета на главной странице такая точность незаметна, а производительность существенно выше.

4 проблема:

Отсутствие данных при старте - сервис не содержит никаких данных

Решение:

Данные накапливаются по мере поступления сообщений из Kafka. Первые минуты после запуска топ может быть пустым - это нормально.

5 проблема:

Как быть, если Kafka недоступна?

Решение:

Сервис продолжает работать с уже накопленной статистикой в памяти, но не получает новые запросы. После восстановления Kafka consumer продолжит чтение с последнего подтверждённого смещения (благодаря Consumer Group).

&#x20;Компромиссы, на которые пришлось пойти:

\- Потеря точности при перезапуске сервиса - все счётчики обнуляются. Принято, потому что «сейчас ищут» не требует персистентности.

\- Кеш топа может устаревать на 2 секунды - допустимо, так как тренды меняются не мгновенно, а виджет всё равно не требует строгой актуальности до миллисекунды.

\- Стоп‑лист хранится только в памяти - при перезапуске сервера стоп‑лист теряется. В реальном проекте стоило бы добавить периодическое сохранение в файл или использовать Redis, но по условию managed‑решения запрещены, а файловое хранилище усложнило бы архитектуру. Для демо‑проекта это допустимо.

\- Защита от накруток работает на уровне пары (user, term) - это эффективно против одного пользователя, но не против распределённой бот‑сети. Для полной защиты потребовался бы более сложный алгоритм (например, скользящая медиана частоты). Однако задание явно указывало на аномалии от «конкурентов или парсеров» (обычно с ограниченного набора IP/аккаунтов), поэтому выбранного подхода достаточно.

&#x20;Производительность (бенчмарки)

Нагрузочное тестирование проводилось с помощью vegeta на ноутбуке (CPU 4 ядра, 16GB RAM).

Сценарий: GET /top?limit=10, 1000 запросов/сек в течение 30 секунд.

Latencies (mean, 95%, 99%): 3.2ms, 7.8ms, 15.3ms

Requests/sec: 1000.03

Success rate: 100%

Пропускная способность сервиса упирается в сеть и CPU, но при горизонтальном масштабировании (несколько инстансов) может быть увеличена.
